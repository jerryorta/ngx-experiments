NgeTable — Row Selection (Interaction)

Interaction is the primary facet for a table feature, and selection is the clearest case: none of the examples below shows anything until you drive it. Every table supplies getRowId — selection is id-keyed state, and without a stable identity the engine keys it by array index, so Example 4's sort would move the ticks onto different records.

1. Click, cmd/ctrl-click, shift-click

Click a row to replace the selection, cmd/ctrl-click to add or remove one, shift-click to take the range from the row you last chose. The anchor does not move on a shift-click, so repeated shift-clicks pivot around the same row — the range can be grown and shrunk, not only ratcheted.

The checkbox is the same affordance, not a separate one: shift-clicking it extends the range exactly as shift-clicking the row body does. It differs in one deliberate respect — a plain checkbox click is additive, where a plain click on the row body replaces. A per-item switch must never clear the rest.

2. Select all, select none, indeterminate

The header checkbox reads all three states. Tick one row and it goes indeterminate; tick every row and it goes checked. Clicking it when it is checked clears the selection.

3. The host drives the selection

The other half of the controlled-state contract, and the half a gesture never demonstrates: these buttons write state from outside and the checkboxes follow. Host-driven state is deliberately silent — it emits no NgeTableEvent, because an echo of the host's own write is not news and would make a two-way binding read as user activity.

4. A selection survives a sort

Select a few rows, then click a header to re-sort. The same records stay ticked and move with the sort — the ticks follow the data, not the positions. Shift-clicking after a sort also takes the range the user can see between the two clicks, because the range is cut from the processed row model rather than from the source array.

5. One row at a time

enableMultiRowSelection: false reduces the whole feature to a single row: no header checkbox, no range, and cmd/ctrl-click and shift-click both fall through to a plain replace. None of that costs the library any code — the engine clears the other keys itself when a row cannot multi-select.

6. Selection across a virtualized scroll — 10,000 rows

⚠️ The example that cannot be written as a unit test. Select some rows near the top, scroll all the way down and back, and they are still ticked. Virtualization recycles DOM, so a mark held on an element would belong to whichever row that element happens to be showing after the scroll; these marks were never on an element at all.

{{ virtualCount() }} of 10,000 selected

7. Selection and pinned columns

Select a row, then scroll horizontally. The pinned lanes are position: sticky and opaque by requirement — a transparent pinned lane would show the center cells bleeding through — so the selected tint has to be repainted on them explicitly. If it were not, a selected row would read as selected in the middle and unselected at both edges.

8. The selection-change event

One kind for every route into the slice — checkbox, click, cmd-click, range, Space, select-all. Note what a range produces: shift-click across five rows and exactly one line appears below, because the gesture writes the whole slice once rather than once per row.

10. A consuming app's own control

The native checkbox is the default, not the only option. Projecting selection-cell and selection-header replaces it with whatever the consuming domain ships — cg-checkbox, gy-checkbox — bound to a context carrying isSelected, canSelect, and a toggle callback. Drive it: the pills below write the same state.rowSelection the native checkbox would.

⚠️ The pill is a local stand-in rather than a real design-library import, because libs/shared/table importing a domain library would invert the dependency graph and drag that domain into every consumer of the table. What it exercises — the context and the callback — is identical either way. Note also that this table's enableRowSelection is a predicate, so archived rows report canSelect: false and render disabled rather than absent: a control that silently vanishes reads as a rendering bug, a disabled one reads as a rule. 

<nge-table [config]="config" [(state)]="state">
  <ng-template ngeTableSlot="selection-cell" [ngeTableSlotOf]="rows" let-selection>
    <cg-checkbox
      [checked]="selection.isSelected"
      [disabled]="!selection.canSelect"
      (click)="$event.stopPropagation(); selection.toggle($event)" />
  </ng-template>
</nge-table>

11. Keyboard

Tab into the table from Example 1 and note what is focusable: the row, not the checkbox inside it. Space on a focused row toggles it. The per-row checkbox is a pointer affordance only (tabindex="-1", aria-hidden) — the row already carries aria-selected, so a focusable checkbox would double the tab stops and announce the same fact twice. The header's select-all checkbox is a tab stop, because it is the only keyboard route to select-all and there is exactly one of it. Full arrow-key grid navigation over a roving tabindex belongs to the later a11y story.
