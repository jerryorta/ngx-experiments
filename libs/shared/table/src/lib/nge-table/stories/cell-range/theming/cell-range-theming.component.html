NgeTable — Cell Range Selection (Theming)

Four tokens, each with a literal fallback at its use site. The addon adds nothing to core's _table-tokens.scss — editing that partial would be a core edit, and the point of this story's feature is that an addon needs none. Every section below is the same table with the same rectangle under a different wrapper class, which is exactly what a consumer writes. There is no config.theme; a table themes through CSS custom properties alone, so this story's substance is its SCSS.

1. The token contract

Four properties, all read from CSS and all themeable from any selector with higher specificity than :root. 

.my-theme {{ "{" }}
  --nge-table-range-surface: #dbeafe;        // the cell tint (must be opaque)
  --nge-table-range-outline: #93c5fd;        // the inset ring on every selected cell
  --nge-table-range-on-surface: #0b2545;     // text on the tint
  --nge-table-range-focus-outline: #1d4ed8;  // the heavier ring on the ACTIVE range's focus cell
{{ "}" }}

⚠️ The namespace is --nge-table-range-*, not --nge-table-selection-*: ARCH-268's row selection already owns that prefix, and a cell range is not a row selection. The two can be lit at once on the same table, and picking colours that survive the overlap is a theme's job.

Opaque is a requirement, not a preference. A pinned lane is position: sticky and scrolls over the center lane, so a translucent tint shows the center cells sliding underneath. Section 6 is where that is visible.

2. Default — no theme applied

The literal fallbacks, which is what a consumer sees before writing a single token. One three-row block spanning status → amount; the cell at amount on the last row is the focus, and carries the heavier ring.

3. Three palettes, one table

Identical config, identical state, three wrapper classes. Theming a table changes nothing about its configuration — which is the whole reason this story is SCSS rather than TypeScript.

4. A subtle wash

Dropping the outline to the tint's own colour leaves a wash rather than a grid of boxes — appropriate when a range means "this is the region you are working in" rather than "you have selected exactly these". The focus ring is deliberately left strong: it is the one mark that carries information a user cannot infer from the block's shape.

5. Dark

The shape a domain's --nge-table-* bridge will take when a consumer adopts the library. Every surface is restated rather than left to inherit — the pinned surfaces especially, which are opaque by requirement, so a missed one shows up as a pale rectangle punched through the table.

6. A selected pinned column

name is pinned left and the block starts inside it. Scroll sideways — the table is deliberately narrowed here, because the fixture's seven columns otherwise fit the panel and there would be nothing to scroll. The tint must stay opaque or the center cells show through the sticky lane.

No pinned-lane rule exists in the addon's stylesheet and adding one would be dead code: this tint is on the cell, which paints over its own lane's background. ARCH-268 needed a sibling rule because its tint is on the row, which a lane paints over. Should a theme make this tint translucent, the fix belongs on the token.

7. Density — and the trap underneath it

This section's wrapper sets --nge-table-row-height and --nge-table-header-height, and it works — because its config omits both fields. Every other table on this page would ignore the same two declarations entirely. 

// ❌ the factory fills rowHeight/headerHeight in, and <nge-table> writes them
//    INLINE on the host — where they outrank any wrapper class, silently
config = createNgeTableConfig<Row>({{ "{" }} columns, data, getRowId {{ "}" }});

// ✅ hand-authored, omitting them — the tokens reach the theme
config: NgeTableConfig<Row> = {{ "{" }} columns, data, getRowId {{ "}" }};

⚠️ It does not compose with virtualization: the virtualizer positions rows it has not rendered at index × rowHeight, so with windowing on the resolved height is always written inline and row height is a config concern whatever the theme says. Cell padding (--nge-table-cell-padding-x / -y) has no such caveat and is the safer density knob.

8. What is and is not themeable here

The addon's four tokens sit in the library's first tier — read straight from CSS, overridable from any wrapper class. The other tiers are worth knowing before reaching for a token that will not answer. 

--nge-table-range-surface          ✅ read from CSS
--nge-table-range-outline          ✅ read from CSS
--nge-table-range-on-surface       ✅ read from CSS
--nge-table-range-focus-outline    ✅ read from CSS

--nge-table-row-height             ⚠️ only when the config omits `rowHeight` (section 7)
--nge-table-header-height          ⚠️ only when the config omits `headerHeight`
--nge-table-column-min-width       ❌ mirrored in TypeScript — the knob is NgeTableConfig
--nge-table-selection-column-width ❌ mirrored in TypeScript — ARCH-268's injected column
--nge-table-internal-*             ❌ never yours to set — runtime lane geometry

One caveat worth stating plainly: because a selected cell is painted with box-shadow: inset rather than a border, it adds no width. A real border would add two pixels the lane arithmetic has not accounted for — column widths are the engine's exact numbers and are user-owned once resizing is on — and every column downstream would drift.
