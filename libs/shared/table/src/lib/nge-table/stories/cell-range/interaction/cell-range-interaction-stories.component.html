NgeTable — Cell Range Selection (Interaction)

A range is an addon, not a table feature: one line of providers, one projected overlay, and no file in the library core changed. Everything here is a gesture. Drag across cells to select a block; shift-click to extend it; cmd/ctrl-drag to add a second, disjoint one. jsdom has no scroll geometry, no sticky offsets and no pointer capture, so this page — not a spec — is where the feature is actually verified.

1. Drag out a rectangle

Press in one cell, drag to another, release. The block is stored as a single descriptor — four ids naming two opposite corners — never as a map of the cells it covers. Which cells lie between those corners is resolved at read time, rows against the processed row model and columns against the visible leaf columns in visual order.

The corner you started from is the anchor; the one under the pointer is the focus, painted with a heavier ring because it is what a keyboard extension would move and where a fill handle (ARCH-271) will sit.

2. Shift-click extends — and the anchor does not move

Click a cell, then shift-click somewhere else. Now shift-click back towards the first cell: the block shrinks. That is the whole reason the anchor stays put — a second shift-click is how a user corrects an over-shoot, and an anchor that followed the pointer would leave a block that could only ever be grown.

Watch anchorRowId / anchorColumnId below hold still while the two focus fields move. It is the same rule ARCH-268 records for row ranges and ARCH-250 for highlight blocks.

3. cmd/ctrl-drag adds a disjoint block

Drag out one block, then hold cmd (ctrl on Windows) and drag out another somewhere else. Both stay. A plain drag replaces, because that is what clicking into a spreadsheet does; cmd/ctrl appends, which is the whole reason the slice holds an array rather than one rectangle.

Only the last rectangle is active — a following shift-click moves that one and leaves the earlier blocks where they were put.

4. Drag past the edge — auto-scroll

Only checkable in a browser. This table is deliberately narrower and shorter than its data. Start a drag and push the pointer past the bottom edge, or past the right-hand edge: the viewport scrolls and the block keeps extending against the cells that arrive, so a selection can exceed what is visible without you letting go.

The speed ramps rather than being flat — nothing at autoScrollThreshold (48px) from the edge, up to autoScrollSpeed (12px per frame) at the boundary and beyond. Nudge the pointer towards the edge and it creeps; shove it well past and it runs. A flat speed makes a long selection either unbearable or uncontrollable, and there is no single value that is both.

It re-hit-tests at the last known pointer position on every frame, because during an auto-scroll the pointer is not moving — the cells under it are.

5. Escape and cmd/ctrl-A — and why only this table has them

Select something here and press Esc: the selection goes, and so does the gesture anchor. Click into this table first, then press cmd/ctrl + A: every cell of the current view is selected as one rectangle, anchored on its own top-left corner so a following shift-click narrows it rather than starting over.

⚠️ This is the only table on the page that answers those keys. Both listeners are on the document — nothing in a table body is focusable, so a scoped handler would never fire — which means several range-enabled tables on one page would all clear on one Esc. Every other section here passes {{ "{" }} clearOnEscape: false, selectAllOnModifierA: false {{ "}" }}. A single-table application should keep the defaults.

The two keys are polite in different ways, and they have to be. Esc never calls preventDefault() and writes nothing on an unselected table, so an Esc meant for a dialog costs nothing. cmd/ctrl-A must take the key to work at all — otherwise the browser also selects the whole document's text underneath — so it is scoped by engagement instead: try it before clicking into the table and the page keeps its own select-all.

6. Ten thousand rows — a range survives a virtualized scroll

The acceptance criterion only a browser can check. Select a block, scroll it far out of view, and scroll back — it is still selected. Virtualization recycles DOM, so the node drawing row 4,000 drew row 12 a moment ago; the selection survives because it lives in state and every render re-derives from there, never because an element remembered anything.

Start a drag and hold the pointer just below the last visible row: auto-scroll runs through the virtual window and the block keeps extending. Then watch slice size barely move. A descriptor is four strings whatever it covers — the same block enumerated per cell would be ~270 KB of JSON re-emitted on every state change, and a few such columns would exceed Firestore's 1 MiB document limit. That breaks the "a user's view can be persisted and restored" property, not merely a frame budget.

7. Pinned columns — the block resolves against visual order

name is pinned left and owner right. Drag a block that starts in the pinned lane and ends in the center, then scroll sideways. A pinned lane is position: sticky and scrolls over the center lane, so a selected pinned cell must stay opaque — a translucent tint would show the center cells sliding underneath it.

Now select a block spanning status through amount and press Pin quantity. The rectangle re-shapes: its corners are column ids, and everything between them is resolved against visual order across the three lanes at read time. This is the axis ARCH-250's highlighting never had — it materialised its column span at write time, so a pin left it describing columns that had moved.

8. A block follows the view; its corners follow their records

Drag out a block, then sort. The descriptor's endpoints are row ids, so they follow their records — but which rows lie between them is resolved against the current sort order, so the block re-shapes rather than travelling intact.

That is a deliberate reading of "the block the user dragged out", inherited from ARCH-250, and it is the one AG Grid's coordinate-based ranges get wrong in the other direction — theirs survive a scroll but not a sort. Note too what a filter does: a focus that is no longer in the model matches nothing, while an anchor that is gone degenerates to the focus alone rather than selecting from index zero.

10. Host-driven state — seed, persist, restore

These three controls all write section 1's table from outside, with no gesture at all — the other half of the controlled-state round trip, and the half a drag never shows. The slice is plain JSON, so a user's selection persists and restores with the rest of their view. Pushing state back in is silent: it emits no NgeTableEvent, or restoring a saved view would replay as a burst of user activity.

⚠️ The gesture anchor deliberately does not travel. It is scratch on the bridge and never reaches state, so after a restore your next shift-click starts a rectangle rather than extending the restored one. Reaching from a corner the user never touched in this session is the alternative, and it is worse.
