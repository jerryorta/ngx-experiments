NgeTable — Cell Textarea Interaction

The table's own long-text editor, and the first whose commit is explicit (ARCH-296). Every section below asks you to do something, and most of them ask you to confirm that something did not happen — so read the edit-intent readout under each table, not the table alone.

1. Apply is the only commit

Click a Description cell to activate it. A panel opens with the text already in it and the caret in the field. Change something and press Apply — the proposal appears below as an edit-intent and the row updates.

The column named NgeCellTextareaComponent through ngeCellTextareaEdit(); there is no [ngeCell] template and no <nge-cell-textarea> tag in the demo's markup.

2. Cancel proposes nothing

Type into a description, then press Cancel. The panel closes, the cell keeps its old text, and the edit-intent readout stays empty.

⚠️ This is the section the whole story turns on. Clicking Cancel blurs the field on its way to the button, and every other editor in this library commits on blur. If a commit-on-blur handler existed here, Cancel would apply the very edit it exists to discard — so there is no blur handler at all, not even a guarded one.

3. A host that ignores the proposal

The same editor against a host that listens and declines to act. Press Apply: the edit-intent arrives and the table does not change.

This section exists to keep two different outcomes legible in every section above it. “The table proposed nothing” and “the host declined to apply” look identical if you watch only the rows. config.data belongs to the host; the library announces a patch and never writes one.

4. Blur proposes nothing, by every route

Activate a cell, type, and then leave the field three different ways, checking the readout after each: click Cancel; press tab until focus reaches Apply without pressing it; and click somewhere outside the panel entirely.

All three fire a real blur on the field. None of them proposes anything. Only pressing Apply does.

5. A dirty draft is protected; a clean one does not detain you

First, dirty: activate a cell, type a few words, then click outside the panel. The panel stays, focus returns to the field, and an Unsaved hint appears beside the buttons. Dismissing there would throw away what you had typed, which is exactly the failure this editor exists to prevent.

Then, clean: activate another cell and click outside without typing. It closes immediately, like any dropdown. And if you type and then undo your typing back to the original text, it closes again — the panel is asking “is anything at stake”, not “did you press a key”.

⚠️ tab is deliberately not trapped, even while dirty. A click outside is refused because it would destroy the draft; tabbing away destroys nothing — the panel stays open, the text stays put, and shift + tab comes back.

6. Scrolling cannot destroy a draft

Establish the baseline first, or this section proves nothing. With no panel open, scroll the table and press Sample viewport scrollTop — it moves. This table is virtualized over 2,000 rows in a short viewport, so a row genuinely leaves the window when you scroll past it.

Now the claim. Activate a description cell, type something, and try to scroll the table — wheel over it, and drag its scrollbar. Nothing moves. Sample scrollTop again and confirm the number is unchanged. Press Cancel and the table scrolls normally again.

⚠️ Why this matters more here than for the select. Rows are tracked by id, so a row leaving the virtualized window is destroyed — the editor dies with it. For a dropdown that costs a closed list. For a textarea it would cost however much prose you had typed, silently, mid-sentence, because you scrolled. So the panel takes a backdrop, and the row simply cannot leave while you are typing.

⚠️ The obvious API does not do this. CDK's scrollStrategies.block() acts on the document element, and this table scrolls in an inner viewport — it would read as implemented and change nothing. The fix is an element in the way, not a strategy.

7. Keyboard, and what esc must not take with it

Drag across a few cells first so state.ngeRange below is not empty. Then activate a description, and try each of:

  • enter — inserts a newline. It never commits; that is why this is a textarea.
  • cmd/ctrl + enter — applies, exactly as the button does.
  • esc — cancels outright and proposes nothing.

⚠️ After esc, check that state.ngeRange is still there. The cell-range and highlight addons both listen for esc on the document, and a panel's keys are dispatched from body — one node earlier. Without the panel stopping the key, closing this editor would silently clear your selection. The panel closing is not evidence that it does; the range readout is.

esc cancels in one press rather than two. The select closes its panel first and cancels on a second press, but its trigger is still a usable control with the panel shut — here a closed panel would leave the cell as plain text with no way back into it.

8. A range drag started on the trigger selects nothing

Activate a description cell, then press and drag from the cell itself across its neighbours. state.ngeRange stays empty. Then drag from a Name cell and watch it fill — which is what makes the first half evidence rather than a table with the feature switched off.

The whole cost of this is one attribute: the trigger declares role="textbox", and the library's interactive-element guard already matches that role. No core change — roles rather than component names, so a consumer's own control gets the same treatment.

9. A consumer's own template still wins

The same column, with a [ngeCell] template projected for it. The library's editor is never reached — clicking a description does not open a panel, because the consumer's markup is what renders.

A library-shipped editor is a default, not a fixture: the slot registry consults projected templates first, then the component a column named. Reversing those two lines compiles, lints and renders perfectly while silently ignoring every consumer template.

10. The options a column can declare

The same editor with rows: 8, maxlength: 120 and a placeholder. Activate a cell and confirm the field is taller, stops accepting input at 120 characters, and shows the placeholder once you clear it.

Options ride editorInputs rather than a top-level meta key, because a cell context carries a column id and no column — an editor cannot read column meta at all. ngeCellTextareaEdit() exists because that bag is Record<string, unknown> and a misspelled key would be dropped in silence; going through the helper makes it a compile error.

⚠️ There is no alwaysLive to pass, and its absence is deliberate. For the select it is a trade — one <button> per row against a click before the click that opens. Here the control is a body-level overlay, so an always-live column would mean one panel per visible row, which is not a rendering of a column at all.
