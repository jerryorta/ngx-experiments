NgeTable — Inline Editing (Interaction)

Inline editing is a cell pattern, not a table feature. A column opts in with meta.ngeEdit.enabled; the cell renders read-only text until cell.isEditing() flips, and the control that appears is the consumer's own [ngeCell] template. No editor ships from the library in this story — those are ARCH-293 and ARCH-294.

Nothing here writes your data. Committing announces an edit-intent and stops; the demo component wrapping each table applies the patch to its own rows. Section 2 turns that listener off to show what the library does on its own.

⚠️ This page needs a human in a foregrounded tab. An untrusted event triggers no browser default, so a scripted space never types a character and a scripted drag never selects text — and an automation tab is visibilityState: 'hidden', which suspends requestAnimationFrame so zoneless change detection never flushes and activation reads as broken when it is not.

1. Activation is the default

Click a cell in Name or Description. An input appears, focused and holding the current value. enter or clicking away commits; esc abandons it. Everything else in the row is read-only and behaves as it always did.

Also try tab to a row and press enter. The row is a tab stop because the table is editable — the same terms on which selection makes it one. ⚠️ It opens the row's first editable column, because without arrow-key grid navigation a focused row carries no notion of which cell. That is what "activate on enter" can honestly mean until that story lands.

The reason activation is the default is arithmetic: thirty visible rows across three editable columns would be ninety control instances nobody asked to edit. Activation never builds them.

2. A host that ignores the intent

The same table with the edit-intent handler switched off. Edit a cell and commit it: the editor opens, the value is collected, the proposal arrives in the readout — and the table does not change.

⚠️ This is correct behaviour, not a bug. The library owns no data, so it announces the patch and waits. A host that has not opted into editing sees no edit. It is the same contract fill-intent established in ARCH-271, and both kinds carry the same NgeCellPatch — so one applyPatches serves both while the two kinds stay distinct, letting a host accept a fill and reject a hand-typed edit.

3. Always-live, and the control the guard exists for

Quantity declares meta.ngeEdit.alwaysLive, so its slider is there without being activated. That is the case the opt-out exists for — a column whose control is the reading, scanned down rather than opened one cell at a time — and it is a per-column decision, never a table-wide mode.

⚠️ The slider is a div carrying role="slider", deliberately not an <input type="range">. A native range input was already matched by the old tag-list guard and would demonstrate nothing. This is the shape a design-library control actually takes. Cell ranges are switched on below — drag the thumb and confirm the value moves and no cells are selected. Then drag on the plain text of a read-only cell beside it: that does sweep a range, which is the contrast.

Arrow keys step it too, so the control is reachable without a pointer.

4. The four keyboard collisions

Row selection and cell ranges are both switched on here, so every shortcut an open editor can collide with is live. Open an editor in Name and work through them:

  • space — types a space. It does not toggle the row's selection, and the page does not scroll. Press it on the row itself (not in the input) and selection toggles as it always did.
  • esc — cancels the edit and leaves your cell range alone. Select a block of cells first, then open an editor and press it: the block is still there. Three addons bind esc at the document; the cell stops the event before any of them sees it.
  • cmd/ctrl + a — selects the field's text, not every cell in the table.
  • cmd/ctrl + space — reaches neither the editor nor the column selection. The column route is scoped to a focused header, which an in-cell editor never is.

⚠️ Also check the thing that would be easy to break: a plain click into an input must focus it. The row suppresses the browser's text-drag on shift-click only, precisely because an unconditional suppression would take focus with it.

5. Scrolling an in-progress edit out of the window

Two thousand rows, virtualized. Open an editor near the top, then scroll it well out of view and come back.

⚠️ The edit is cancelled, and that is the point. Virtualization recycles DOM — the element that rendered your row now renders a different one — so a draft that survived would land on whichever record took the slot. That failure reads as data corruption rather than as a bug, which is why the edit is abandoned instead. Nothing is proposed: the readout stays as it was.

The same rule covers a row leaving the row model for any other reason — a filter, a sort that drops it, or new data arriving.
