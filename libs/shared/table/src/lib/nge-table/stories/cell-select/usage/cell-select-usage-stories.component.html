NgeTable — Cell Select Usage

A column declares its choices and names the editor; the table renders it. No [ngeCell] template, no @tanstack/* import, and no <nge-cell-select> tag in the consumer's markup.

1. Declaring a select column

ngeCellSelectEdit() builds the ngeEdit meta for you. Options are primitives — a label the user reads and a value the table proposes.

import {{ "{" }} ngeCellSelectEdit {{ "}" }} from '@nge/table/editors';

const STATUS_OPTIONS = [
  {{ "{" }} label: 'Active', value: 'active' {{ "}" }},
  {{ "{" }} label: 'Pending', value: 'pending' {{ "}" }},
  {{ "{" }} label: 'Archived', value: 'archived', disabled: true {{ "}" }},
  {{ "{" }} label: 'Failed', value: 'failed' {{ "}" }},
];

const columns = [
  {{ "{" }}
    accessorKey: 'status',
    header: 'Status',
    id: 'status',
    meta: {{ "{" }} ngeEdit: ngeCellSelectEdit(STATUS_OPTIONS, {{ "{" }} label: 'Edit status' {{
            "}"
          }}) {{ "}" }},
  {{ "}" }},
];

2. Why the options ride editorInputs

The helper expands to the shape below. ngeExport (ARCH-248) and ngeFill (ARCH-271) are top-level meta keys because the table's core reads them. An editor's options are read by the editor, and a NgeCellContext carries no column — so editorInputs, which the adapter spreads as component inputs, is the only channel there is. A top-level ngeSelect key would mean core learning what a select is.

meta: {{ "{" }}
  ngeEdit: {{ "{" }}
    editor: NgeCellSelectComponent,
    editorInputs: {{ "{" }} label: 'Edit status', options: STATUS_OPTIONS {{ "}" }},
    enabled: true,
  {{ "}" }},
{{ "}" }}

⚠️ Prefer the helper to writing this by hand. editorInputs is Record<string, unknown> and the adapter applies only keys the component declares as inputs — so {{ "{" }} items: … {{ "}" }} is dropped in silence and the panel renders empty, which reads as a data problem rather than a typo.

3. Reacting to the proposal

The table never writes to config.data. It emits an edit-intent carrying a NgeCellPatch — the same shape fill-intent uses, so one handler serves both — and the host applies it and hands new data back in.

onEvent(event: NgeTableEvent<Row>): void {{ "{" }}
  if (event.kind !== 'edit-intent') return;

  // event.cells: {{ "{" }} columnId, rowId, value, previousValue {{ "}" }}[]
  this.rows.update(rows => applyPatches(rows, event.cells));
{{ "}" }}

4. Shadowing it with your own control

A library editor is a default, not a fixture. A [ngeCell] template for the same column wins, because NgeTableStore.cellTemplate consults projected registrations before the editor a column named. Grouped options, per-option templates and async loading are all reachable this way today — that seam is why the select itself stays a flat list.

<nge-table [config]="config()">
  <ng-template ngeCell="status" [ngeCellOf]="rows" let-cell>
    <strong>{{ "{{" }} cell.row.status {{ '}}' }}</strong>
  </ng-template>
</nge-table>

5. What it deliberately is not

  • Not a form control. No ControlValueAccessor, no NgControl, no validation, no touched/dirty. That per-instance saving is the whole reason the table owns an editor rather than reaching for a design-library select.
  • Not a rich picker. A flat @for over primitives, with no per-option template and no content projection — those are most of what makes a design-system select expensive to instantiate.
  • Not always built. Activation means the panel is constructed when a user engages the cell, so thirty visible rows cost zero overlays.
  • Not @angular/cdk in your table bundle. The CDK is a dependency of @nge/table/editors alone; the production barrel never reaches it, and a spec asserts so against the module graph.
