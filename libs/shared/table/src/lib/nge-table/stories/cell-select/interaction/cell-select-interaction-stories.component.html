NgeTable — Cell Select Interaction

The table's own enum editor, over a CDK overlay (ARCH-294). Every section below asks you to do something: the panel does not exist until it is opened, so none of what this story is about survives a screenshot.

1. The select, with no template written

Click a Status trigger to open it. Choose an option and the proposal appears below as an edit-intent. The column named NgeCellSelectComponent through ngeCellSelectEdit(); there is no [ngeCell] template and no <nge-cell-select> tag in the demo's markup.

⚠️ The trigger is there at rest, and that is the default — ngeCellSelectEdit() declares the column alwaysLive. A cell rendering as bare text gives a user no way to know the column is a select, and activation would cost a click before the click that opens; what it saves is one <button> per visible row. The expensive half is deferred either way — no overlay, portal or option list exists until something is opened. Section 9 shows the opposite trade.

2. The panel is not clipped, and the cell still clips

This table is deliberately narrow and short. Open a status select on the last row and confirm the panel overhangs the table's bottom edge rather than being cut off at it — while the Name and Owner cells beside it still truncate with an ellipsis.

Both halves matter. .nge-table__cell keeps overflow: hidden and stays unpositioned so pinned lanes remain sticky (ARCH-243); the panel escapes anyway because the CDK attaches it to a container on <body>. If the panel were clipped, the overlay is not doing its job; if the neighbouring cells stopped truncating, the substrate has been broken to make room for it.

3. An open panel follows its trigger, then vanishes with its row

Open a status select, then scroll the table gently — the panel tracks the trigger. Now keep scrolling until that row leaves the window: the panel disappears rather than drifting or hanging in place.

Those are one mechanism, not two. Rows are @for-tracked by row.id, so a row leaving the window is destroyed rather than recycled onto another record — the editor dies with it and its DestroyRef teardown disposes the overlay. So RepositionScrollStrategy gets the close-on-exit for free, and the detached-node fear that makes CloseScrollStrategy look like the safe choice never materialises: measured at 25px per frame, thirteen frames tracked exactly and none was positioned at the detached {{ "{" }}0,0,0,0{{ "}" }} origin.

⚠️ This depends on rows being destroyed rather than recycled. Row recycling is an unticketed backlog item for this epic; if it lands, a recycled trigger stays connected while showing a different record and the panel would follow the wrong row. The strategy has to be revisited before that ships.

4. The two-stage esc — and the cell range it must not clear

Cell ranges are on. In this order:

  1. Drag across three or four cells in the Quantity column — the state.ngeRange readout fills in.
  2. Activate a Status cell and open its panel. This section runs with alwaysLive: false deliberately, so there is an activation for the second press to cancel and both stages are visible.
  3. Press esc once. The panel closes, the cell is still being edited, and state.ngeRange is unchanged.
  4. Press esc again. The edit cancels. The range is still unchanged.

Why this needed two mechanisms rather than one. ARCH-292 contains esc by stopping it at the cell, which starves the range and highlight addons' document-level listeners because document is last on the bubble path. A panel attached to <body> is not on that path at all — CDK dispatches its keys from a body listener, one node earlier — so stage one is claimed at the panel, and a trigger handler guarded on the panel being open covers the case where focus never left the trigger. With no panel open, esc is left completely alone.

5. A range drag started on the trigger selects no cells

Activate a Status cell, then press and drag from the trigger itself across neighbouring cells. state.ngeRange stays empty. Now drag from the Amount cell beside it — it fills. The contrast is the assertion; an empty readout on its own would equally suggest ranges were never wired up.

This costs no new code. NGE_INTERACTIVE_SELECTOR matches on role, and the trigger declares role="combobox" — so the drag guard, and cmd/ctrl+a and shift+arrow containment, all arrive with the attribute.

6. Keyboard

  • enter on a focused row activates the row's first editable column.
  • enter, space, ↑ or ↓ on the trigger opens the panel.
  • ↑ ↓ move through the options and skip Archived, which is declared disabled.
  • home and end jump to the first and last selectable option.
  • Typing jumps by prefix — press f for Failed. The buffer clears after half a second, so pe finds Pending while p … pause … e does not.
  • enter commits the option under the cursor.

The option under the keyboard is announced through aria-activedescendant rather than by moving focus: focus stays on the panel itself so its keys reach CDK's body listener, which is what makes stage one of esc possible.

7. A consumer's own template still wins

The same column, with a [ngeCell] template projected for status. The uppercase badge renders and <nge-cell-select> is never reached — NgeTableStore.cellTemplate consults projected registrations first. A library editor is a default a consumer shadows, never a fixture they have to work around.

8. A host that ignores the proposal

Same table, but the host does not apply what arrives. Choose an option: the edit-intent is emitted and the cell reverts. The library never writes to config.data — it announces a patch and the host owns whether anything changes.

9. The other trade — alwaysLive: false

The same column left on activation. Cells render as read-only text and a click activates before a second click opens — which is the right trade for a dense, read-mostly grid where a trigger per row would be visual noise, and the wrong one where a user needs to see that the column is editable at all.

Worth comparing against section 1 directly. Neither costs an overlay at rest; the whole difference is one <button> per visible row against a user's ability to tell what the column does.
