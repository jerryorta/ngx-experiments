NgeTable — Cell Highlighting (Theming)

Three tokens, each with a literal fallback at its use site. The addon adds nothing to core's _table-tokens.scss — editing that partial would be a core edit, and the point of this story's feature is that an addon needs none. Every section below is the same table with the same marks under a different wrapper class, which is exactly what a consumer writes.

1. The token contract

Three properties, all read from CSS and all themeable from any selector with higher specificity than :root. 

.my-theme {{ "{" }}
  --nge-table-highlight-surface: #fff3bf;      // the cell tint (must be opaque)
  --nge-table-highlight-outline: #f0c000;      // the inset ring
  --nge-table-highlight-on-surface: #1f1a00;   // text on the tint
{{ "}" }}

Opaque is a requirement, not a preference. A pinned lane is position: sticky and scrolls over the center lane, so a translucent tint shows the center cells sliding underneath. Section 6 is where that is visible.

2. Default — no theme applied

The literal fallbacks, which is what a consumer sees before writing a single token. Two individually-picked cells and one two-column block.

3. Three palettes, one table

Identical config, identical state, three wrapper classes. Theming a table changes nothing about its configuration — which is the whole reason this story is SCSS rather than TypeScript.

theme-amber (default)
theme-mint
theme-violet

4. A subtle mark

Dropping the outline to the tint's own colour leaves a wash rather than a box — appropriate when highlighting means "these rows matched" rather than "you selected these".

5. Dark

The shape a domain's --nge-table-* bridge will take when a consumer adopts the library. Every surface is restated rather than left to inherit — the pinned surfaces especially, which are opaque by requirement, so a missed one shows up as a pale rectangle punched through the table.

6. A highlighted pinned column

name is pinned left and highlighted. Scroll sideways. The tint must stay opaque or the center cells show through it — which is why the addon's stylesheet restates the surface for the pinned lanes rather than relying on the cell rule alone.

7. What is and is not themeable here

The addon's tokens sit in the first tier of the library's five — read straight from CSS, overridable from any wrapper class. Nothing about highlighting falls into the other tiers, and in particular it declares no geometry: a highlight paints inside a cell whose size the engine already owns. 

--nge-table-highlight-surface      ✅ read from CSS
--nge-table-highlight-outline      ✅ read from CSS
--nge-table-highlight-on-surface   ✅ read from CSS

--nge-table-internal-*             ❌ never yours to set — runtime lane geometry

One caveat worth stating plainly: because a highlight is painted with box-shadow: inset rather than a border, it adds no width. A real border would add two pixels the lane arithmetic has not accounted for, and every column downstream would drift.
