NgeTable — Row-Detail Content Usage

A cell is bounded by a column width; a row-detail band is as wide as the table. That difference is the whole reason the band exists, and since ARCH-298 gave it a declared height it can hold content that needs one — charts above all. Nothing on this page is a table feature: a band's content is your own markup, and this story adds no library code. No example here imports @tanstack/*.

1. Two charts, side by side, in one band

The band is a flex row and each chart is a column of it. Two independent interactive charts fit where a cell could not have held one legibly — and both are built from the same twelve numbers already on the row (series, from the shared ARCH-290 fixture), read straight off detail.row.

2. The height contract — the one rule you have to write

<nge-chart> attaches a shadow root injecting :host, svg {{ "{" }} width: 100%; height: 100% {{ "}" }}, and a percentage height resolves against nothing when its parent's height is auto. So a chart in a band with no declared height collapses to a 0px-tall nothing — silently, with no error anywhere.

The band has a height. It does not, however, hand it down: the band is a plain block. So the content reads the same custom property the table was sized by — one declaration, correct in both height regimes, and no number duplicated between your SCSS and your config. 

.detail-band {{ "{" }}
  box-sizing: border-box;
  display: flex;
  height: var(--nge-table-row-detail-height, 120px);   /* ← the contract */
  padding: 12px 16px;
{{ "}" }}

.detail-band__chart {{ "{" }} display: flex; flex: 1 1 0; flex-direction: column; min-width: 0; {{
            "}"
          }}
.detail-band__plot  {{ "{" }} flex: 1 1 auto; min-height: 0; {{ "}" }}

min-height: 0 on the plot is load-bearing too. A flex item's automatic minimum size is its content, and an SVG's content is not small — without it the plot refuses to shrink and pushes the band's fixed height into a scrollbar instead of fitting inside it.

3. Why a chart cell's sizing does not transfer here

The Chart Cells story sizes its chart with align-self: stretch, and it is reasonable to expect the same move one level out. It does not work, and the reason is worth knowing rather than discovering: 

/* A CELL is a flex ITEM on a row whose height is already definite. */
.chart-cell  {{ "{" }} align-self: stretch; {{ "}" }}            /* ✅ stretches to the row */

/* A BAND is a BLOCK on its own line — no flex line to stretch against. */
.detail-band {{ "{" }} align-self: stretch; {{ "}" }}            /* ❌ no-op; chart collapses */
.detail-band {{ "{" }} height: var(--nge-table-row-detail-height, 120px); {{ "}" }}  /* ✅ */

.nge-table__row-detail is a block spanning the row (the row carries flex-wrap: wrap so the band lands on its own line). There is no flex line to stretch against and nothing above it to inherit a height from — so the content claims the height explicitly, which is what the rule in Example 2 does.

4. Memoise the chart config by the row object

A factory called straight from the template allocates a new config on every change-detection pass, so <nge-chart>'s config input changes identity and the chart re-renders. Memoise it — and key the cache on the row object, not on row.id: a Map never forgets a row it has seen, so a full virtualized scroll would end up holding a config for every row in the dataset. The row object is also the correct key on its own merits, since sorting and filtering reorder and rewrap rows but never replace the underlying datum. 

private readonly trendConfigs = new WeakMap<Row, NgeChartConfig>();

trendConfigFor(row: Row): NgeChartConfig {{ "{" }}
  const cached = this.trendConfigs.get(row);
  if (cached) {{ "{" }} return cached; {{ "}" }}

  const config = createLineChartConfig({{ "{" }} data: buildTrendSeries(row), … {{ "}" }});
  this.trendConfigs.set(row, config);
  return config;
{{ "}" }}

Building every config eagerly up front is not the alternative — it only trades a scroll stall for a startup stall. If the config depends on something that can change (a control, a theme), rebuild the whole cache when that dependency moves rather than reaching into it; the Interaction story shows that shape.

5. Band content must be a pure function of its row

Virtualization recycles DOM, so a band's element is handed a different row as the user scrolls and the template runs again against it. Content that derived anything from Math.random(), or cached a value on the element, would redraw itself mid-scroll — and would show one row's numbers under another row's name. 

// ✅ Everything traces to the row it was handed.
function buildLagCloud(row: Row) {{ "{" }}
  return LAGS.flatMap(lag =>
    row.series.slice(0, -lag).map((value, i) => ({{ "{" }}
      seriesId: `Lag ${{ "{" }}lag{{ "}" }}`, x: value, y: row.series[i + lag],
    {{ "}" }})));
{{ "}" }}

// ❌ Redraws itself every time the window recycles this element.
const jitter = () => Math.random() * 10;

Both charts above obey this: the lag cloud plots the row's series against itself, and the trend line adds a trailing mean and a level derived from row.quantity. Nothing is invented, so scrolling a band past the window and back draws the identical picture.

6. One height regime, and why the same rule serves every table

The band takes a definite height plus overflow: auto whether or not the table is windowed. Windowing is what makes it load-bearing — the virtualizer was told an expanded row is rowHeight + rowDetailHeight tall and placed the rows beneath it on that basis, so content past the declared height must scroll rather than push its neighbours. Un-windowed nothing is positioned by arithmetic, so the definite height is not strictly required there; it is what the two regimes agree on so the band's open can be animated, which needs two definite endpoints.

Because the content reads the token rather than either rule, one declaration covers both. 10,000 rows below, windowed, with a row already open:

@if (detail.isExpanded) {
{{ detail.row.name }} — trend over 12 days
Same series against itself, at three lags
}

7. One height per table — and what to do when you need two

rowDetailHeight is per table, not per row, and that is a decision rather than an omission. It feeds estimateSize, so a per-row callback would turn one number you set once into a function you can get wrong per row — and the failure mode is expanded rows overlapping their neighbours. A uniform band is also what keeps a table readable: bands you can compare down the column beat bands that each size to their own content.

Two things follow, and the second is the one that makes the first liveable. When two band kinds genuinely want two heights, run two tables — it costs a config object, keeps every band inside one table comparable, and cannot go wrong per row. And within a table, the content is pitched at the height you chose: the 160px band below drops the legend, axis labels and gridlines that the 320px band above affords, because that chrome is ~75px and would leave the plot a sliver. The band height is the constant; the content adapts to it. 

compactConfig = createNgeTableConfig<Row>({{ "{" }} …, rowDetailHeight: 160 {{ "}" }});
bandConfig    = createNgeTableConfig<Row>({{ "{" }} …, rowDetailHeight: 320 {{ "}" }});

// …and the 160px band's chart drops what it has no room for:
createLineChartConfig({{ "{" }}
  data: buildTrendSeries(row),
  legend: {{ "{" }} enabled: false {{ "}" }}, showXAxis: false, showYAxis: false, showPoints: false,
{{ "}" }});
