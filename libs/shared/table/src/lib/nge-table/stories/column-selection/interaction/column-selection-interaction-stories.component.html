NgeTable — Column Selection (Interaction)

Selecting a column is not a new concept: it writes the same ngeRange slice a cell drag writes, as a rectangle whose row endpoints are null — "every row of the view". Everything here is a gesture. Hover a header to reveal the strip on its leading edge, click it to take the column, shift-click another to take the span, cmd/ctrl-click to add or drop one. jsdom lays nothing out, so this page — not a spec — is where the affordance's position, its reveal, and its clearance from the resize grip are actually verified.

1. Click the strip on a header's leading edge

Move the pointer onto any header. A thin strip appears on its leading edge — the opposite end from ARCH-244's resize grip, which half-overhangs the trailing one. Click it and the whole column is selected, painted by the very same overlay that paints a dragged block.

Read the slice below: anchorRowId and focusRowId are null. The mark names no record at all, which is what makes it one object whatever the row count — and what no sort can move.

2. The strip selects; the header still sorts

This is the conflict the story exists to resolve, so drive both. Click the header's label — it sorts, and nothing is selected. Click its strip — the column is selected, and the sort does not move. Alternate between them and watch the two slices below change independently.

A modifier-based split was rejected because shift and cmd are already spent on span-and-disjoint; moving the sort onto an explicit control was rejected as too large a change to established behaviour. The cost of the strip is a target to find, which the hover reveal is there to pay.

⚠️ This table also has resizing on, which makes it the crowded-header case. Three affordances now share one element: the sort on the label, the resize grip half-overhanging the trailing edge, and the selection strip on the leading one. Drag a column boundary and then click a strip on the same header — neither takes the other's gesture, and the strip carries no z-index precisely so the grip keeps the few pixels where they meet.

3. Shift takes the span of columns

Click one strip, then shift-click another. Everything between them, in visual order, is selected. Shift-click back towards the first and the span shrinks — the anchor column stays put, exactly as an anchor cell does for a dragged block.

Try it after dragging out a cell block first: the shift-click unbounds the row axis, so a two-row band becomes full columns. That is the one place anything moves an anchor, and it is deliberate — a user who shift-clicks a header is asking for columns.

4. cmd/ctrl adds a disjoint column — and drops it again

Hold cmd (ctrl on Windows) and click several strips. Each column is added. Now cmd-click one of them again: it is removed.

⚠️ That toggle is a deliberate asymmetry with a cmd-clicked cell, which only ever appends. A column is a named thing a user picks off a list, so un-picking it by clicking again is the obvious reading; a cmd-clicked cell is the corner of a rectangle they are about to drag, and removing it would fight the drag that follows.

5. The keyboard route — cmd/ctrl + Space

Tab until a header cell has focus, then press cmd/ctrl + space. The column is selected; add shift to extend the span. It is the spreadsheet standard, and it reaches what the strip reaches without the strip being a tab stop of its own.

⚠️ It cannot collide with the header's own enter / space sort toggle, and that is structural rather than lucky: Angular's keydown.space binding matches only when no modifiers are held, so a modified press never reaches it. Press plain space on the same header to see the sort take it instead.

This is also the only one of the addon's three shortcuts scoped by focus rather than by engagement — a header cell is a real tab stop, so "which column did the user mean" has an answer here that cmd-A never has.

6. A sort cannot shrink it

Select a column, then sort the table from outside with the buttons below. Every cell of that column is still selected — and the slice has not changed at all.

⚠️ This is the acceptance criterion the nullable row endpoints exist for. Stored as a span between the first and last records, a column selection would follow those two rows through the sort and quietly become whatever now lies between them. Naming no record is what makes the re-sort a no-op here.

7. A pinned column selects the cells under its own header

Select a span of columns, then pin status to the left lane. It moves out from between the endpoints rather than joining them, so the block narrows — because the column axis resolves against visual order across the three lanes, not declaration order.

A pinned lane is position: sticky and scrolls over the center lane, so a selected pinned header and its cells must stay opaque. Scroll sideways and check nothing shows through.

8. Ten thousand rows, and four strings

Select a column, scroll to row 9,000, and it is selected there too. Nothing was enumerated: a recycled node re-derives from state on every pass and holds no mark of its own. Scroll back and the selection is exactly where it was.

Enumerating one column of this table as a per-cell map would be roughly 270 KB of JSON re-emitted on every stateChange, and a few such columns would exceed Firestore's 1 MiB document limit — which does not merely cost frames, it destroys the "a user's view can be persisted and restored" property the descriptor exists for.

9. One slice, so export composes for free

Select whole columns from the header, drag out cell blocks in the body, or both at once — they land in the same array of rectangles. Then export what is selected. readNgeExportData({{ "{" }} cellPredicate {{ "}" }}) has never heard of column selection, and nothing in this addon imports the export seam; they meet on the table and nowhere else.

⚠️ Not one file under src/lib/export/ changed for this story, and neither did ARCH-269's own path. That is the point of expressing a column as a range rather than as a second kind of mark.
