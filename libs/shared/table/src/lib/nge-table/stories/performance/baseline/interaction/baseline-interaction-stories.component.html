NgeTable — Scroll Baseline (Interaction)

Every other story here demonstrates a behaviour. This one produces the reference number the others are read against. The library has claimed since Wave 0 that ten thousand rows cost a DOM of tens and that scrolling them stays smooth, and Wave 6 is about to put charts and editors inside those cells on the strength of that claim — so the claim needs an instrument before it takes any more weight.

⚠️ This table is deliberately plain and must stay that way. A virtualized table and nothing else — no striping, no selection, no editors. Its value is being the unfeatured case, so a feature story's numbers mean something next to it. Adding a feature here would leave it named "baseline" while measuring something else.

⚠️ Baselines are per-machine and measured fresh, never hard-coded. Frame timings depend on the CPU, the display's refresh rate, and whatever else the machine is doing. On a new machine: run this story, then run the feature story, and compare the two there. The Display tile reports the measured refresh rate so you can tell whether two figures are even comparable.

⚠️ Only works in a real browser. jsdom lays nothing out, so the virtualizer builds no window, so there is nothing to scroll and no frame to time. The arithmetic behind the readout is unit-tested; the driving of it cannot be.

4. What each number is for

Dropped is the one that means "it stuttered": frames past 1.5× this display's own measured frame interval, so a missed vsync rather than an assumed 60Hz. p95 sits beside worst frame because one stall is ordinary — a collection, the browser doing something else — while a p95 well above the frame interval means most frames are late, which is what a person actually perceives.

⚠️ There is deliberately no "frames over 16.7ms" count. An earlier version had one, and measured across eight runs it ranged 29%–48% while p95, worst frame and dropped frames all held still — the threshold sat on the 60Hz refresh interval, so jitter relocated dozens of frames across it. Lateness only means something relative to the display's own cadence, which is what Dropped measures.

Rows built is the one to watch across Wave 6. It counts row elements the browser had to construct during the run, and a window slide pays that cost whatever the cells contain — so deferring a chart's contents cannot reduce it. It is therefore the number that decides whether row recycling is worth its own story, rather than a matter of opinion.

Rows in DOM against the dataset size is the virtualization claim itself, stated as two numbers instead of a sentence.
