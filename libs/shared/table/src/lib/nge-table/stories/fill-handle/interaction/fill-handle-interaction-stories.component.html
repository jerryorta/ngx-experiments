NgeTable — Fill Handle (Interaction)

Select a block of cells, then drag the small square at its edge. The values extend into the swept region — but not because the table wrote them. The table computes an intent, announces it as a fill-intent event, and the demo component wrapping each table applies it to its own rows. Section 5 turns that listener off to show what the library does on its own: nothing. jsdom has no pointer capture, no auto-scroll and no touch-action, so this page is where the feature is actually verified.

1. Copy — drag one cell down

Click a single cell to select it, then drag its handle down a few rows. The value repeats. A single source cell is not a series — there is no second value to infer a step from — so it copies.

Select two or more cells of text and the block cycles: a three-cell pattern repeats every three rows, exactly as a spreadsheet does.

Notice what happens on release: the selection grows to cover what you filled, and the grip moves to the new bottom edge — so you can drag straight on to extend further without re-selecting. Only the block you dragged from reshapes; disjoint blocks you added with cmd/ctrl are left alone.

2. Linear series — drag two numbers down

Select two cells in quantity or amount and drag down. The values continue the arithmetic rather than repeating it. The step is taken across the whole source — (last − first) / (n − 1) — so a three-cell source of 1, 3, 5 continues 7, 9 rather than reading only the last pair.

A source whose numbers are all equal has a step of zero, which repeats the value. That is the right answer and needs no special case — and it is why "not a series" is a distinct answer from "a series whose step is zero".

3. Backwards, and sideways

Drag the handle up from a numeric pair and the series descends — 10, 20 extended upward gives …, −10, 0, never 30. Backwards changes the arithmetic, not just the order.

The gesture is two-dimensional: drag the grip diagonally and both axes move at once. The grip drags the far corner and each axis resolves on its own, so a single drag can grow the rows while shrinking the columns.

⚠️ Growing both axes leaves a corner quadrant that belongs to neither the source's rows nor its columns, so the fill runs in two passes: rows first from the real source, then columns across every row — including the ones just produced. The corner is therefore derived from derived values. It is deterministic, and it is the only reading available, since nothing in the source points at it. Excel declines diagonal fills rather than take it; this takes it.

4. Cancelling, and dragging nowhere

Start a drag and press esc before releasing: the outline disappears, nothing is proposed, and the selection you were filling from is still there. A cancelled fill gives up the gesture, not the selection.

Then drag the handle back inside the block. The cells about to leave grey out, and on release the selection shrinks to what is left — with the grip on the new corner. Nothing is proposed and no value changes; the readout below stays put.

⚠️ A spreadsheet also clears the cells you drag back over. That is deliberately not done here: clearing is a change to data, and what "cleared" means — null, empty string, a type's zero — belongs to a host's schema rather than to this library. Shrinking is pure interaction state, which it does own.

The source stays fixed for the whole gesture, so dipping back inside and then dragging out again fills from where you started, not from whatever the block momentarily became.

5. A host that ignores the intent — the contract, made visible

⚠️ This is the section that matters. The same handle, the same drag, the same event — and the table never changes, because this demo's listener does not apply it. The proposal still arrives; read it below.

The library owns no data and must never acquire any. Every other feature reads config.data and writes NgeTableState; this one reads data and writes an event. A host that has not opted into editing gets a fill handle that proposes and a table that stays exactly as it was supplied.

6. The fill follows the view, not the data

Sort the table, then fill down. The proposal names the rows you can see, in the order you see them — resolved against the processed row model rather than the source array. Filling down a sorted table any other way would scatter values across records the user never dragged past.

7. A column that refuses to be filled

status carries meta.ngeFill.enabled: false. Select across it and fill: its neighbours change and it does not. It is excluded as a target only — its values still seed a neighbour's series, which is what a derived or read-only column wants.

8. No handle on a whole-column selection

This table is seeded with a whole-column selection — the shape a header strip (ARCH-270) or cmd/ctrl-A produces. Every cell of quantity reads as selected and no handle appears anywhere. Select a couple of cells normally and the grip comes straight back.

It is seeded rather than typed because every table on this page passes selectAllOnModifierA: false — the listener is on the document, and nine tables would fight over the key.

⚠️ That is ARCH-270's consequence rather than an oversight. A whole-column mark has null row endpoints — it names no record, which is what makes it survive a sort — so it has no bottom corner to hang a grip off and nothing below it to extend into. Materialising rows to give the handle somewhere to sit would silently turn "this whole column" into "these rows of it".

9. Ten thousand rows

Select two cells near the top and drag the handle to the viewport's bottom edge — the table auto-scrolls (ARCH-269's mechanism, reused) and the fill keeps going. Release far down the table and the proposal covers every row swept, including the ones no window ever rendered.

The pending outline survives the scroll because it is derived from row ids on every render, never held on the recycled elements it is drawn over.

⚠️ The live selected data readout is switched off for this table alone. readNgeExportData walks every row of the processed model — ~170–230 ms at 10,000 rows × 7 columns — and the readout recomputes on every state change, which during a drag is every frame. On the twelve-row tables above that is 84 cells and free; here it would make the drag unusable. Which is itself the reason the other stories put the export behind a button.
