NgeTable — Row Expansion (Interaction)

Wave 0 shipped the row-detail slot and left state.expanded for a host to write. What was missing was something a user could touch, and an answer to what an expanded band costs a virtualized table. Example 2 is that answer, and it cannot be checked anywhere but a browser: rows are positioned from sizes the virtualizer was handed, so a band the arithmetic does not know about puts its row on top of the next one — a failure that is visual rather than thrown, and invisible to jsdom, which lays nothing out at all.

1. The flag, on and off

enableRowExpansion defaults to false, and with it off the table renders exactly as it did before the feature existed — no injected column, no chevron, nothing added to the tab order. Toggle the control in the Storybook panel and only the leading column appears.

@if (detail.isExpanded) {
{{ detail.row.name }} owner: {{ detail.row.owner.name }} quantity: {{ detail.row.quantity }}
}

2. A detail band in a virtualized table

Ten thousand rows at 40px each, with a band declared at 160px — four times a row's height, so an overlap would be unmistakable rather than a subtle seam. The band's height is declared (config.rowDetailHeight) rather than measured, because virtualization needs every row's size to be computable before it is rendered.

Open a row near the top. The row beneath it moves down by the band's height rather than being covered by it, and the scrollbar grows by exactly that much. Then scroll: the band travels with its row and the spacing below stays correct the whole way.

What proves it rather than suggesting it: open a row, scroll to the very bottom, and confirm the last row is still fully reachable. A window whose total size had not grown would end one band short.

3. Expand-all writes a shorthand, not ten thousand keys

state.expanded is Record<string, boolean> | true, and the true is not a convenience — it is what makes expand-all affordable at scale. Press the header chevron and read the state below: one boolean, not a map with an entry per row.

The consequence every reader carries: a predicate treating this slice as a Record is wrong for exactly the gesture most likely to produce a large payload. The band arithmetic, the chevron rendering and the emitted event all handle it.

@if (detail.isExpanded) {
{{ detail.row.name }} {{ detail.row.owner.name }}
} 
state.expanded = {{ expandAllJson() }}

4. Disabled, never absent

enableRowExpansion also takes a predicate over the row datum, so only some rows can be opened — here, the {{ gatedOpenableCount() }} of {{ rows.length }} whose quantity is above 250. The rows it rejects keep their chevron and render it disabled: a control that silently vanished would read as a rendering bug, where a disabled one reads as a rule.

6. A domain's own disclosure control

The native chevron is the default, not the only option. Project expand-cell and expand-header and the table wears the consuming app's control instead. The context carries isExpanded, canExpand and a toggle callback, so a projected control inherits the capability check without knowing it exists.

⚠️ The projected template is consulted first and the native control is the @else. Written the other way round a consumer's template would be silently ignored — a central switch standing in front of a seam, which is exactly what the epic's extensibility gate audits for. A projected control also owes itself a $event.stopPropagation(), since it sits inside a row whose click may select.

@if (detail.isExpanded) {
{{ detail.row.name }} opened by a projected control, not the library's own
}

7. The host drives it, and the table stays quiet

Expansion is ordinary controlled state, so a host can write the slice with no gesture at all — which is what Wave 0 shipped, and what restoring a saved view does. The buttons below write state.expanded from outside the table.

⚠️ Host-driven state emits nothing. Only changes the engine routed announce themselves, or restoring a saved layout would replay as user activity in a consumer's log. Watch the event list: it moves for a chevron and stays still for a button.

9. The band animates; the rows beneath do not

The band's height is declared, and a declared height is a transitionable one — so the open is a plain CSS transition with no measurement anywhere. The usual accordion blocker is that height: auto cannot be animated, which is what pushes implementations into JavaScript measurement or a FLIP library; example 2's decision removed it.

The rows beneath jump, deliberately. Animating them means transitioning top, and transform is banned in this library because it creates a stacking context that breaks the sticky pinned lanes. That is also what rules out GSAP: its FLIP plugin — the standard tool for exactly this problem — animates by applying transforms, so it lands on the same wall as a hand-rolled version, having added a runtime dependency. top transitions layout rather than the compositor, on every rendered row, against the frame budget the performance baseline froze.

⚠️ Open and close a row in each table. The two regimes differ, and the difference is not a bug. The left table is in normal flow, so the rows beneath simply follow the band — free from the layout, no code involved — and both directions animate. The right table is windowed: its rows take their new positions in one frame and the band grows into the space they made, so the close is instant. A closing band would go on painting underneath a row that has already moved back over it. The band animates in the direction where the space already exists.

Two independent switches turn it off. Drive duration to 0ms for the consumer's escape — no media query needed. For the accessibility one, set prefers-reduced-motion: reduce in DevTools → Rendering → Emulate CSS media feature prefers-reduced-motion; the band and the chevron both stop moving, whatever the token says.
